# newera-plus: architecture for the job aggregator rebuild

## Objective

Rebuild the job aggregator from an empty repository. The product keeps three principles from the first version: it scrapes job postings, it ranks them against the user's CV, and it shows the result in one interface.

The work is done when a clean container can do this without manual repair: import a CV, fetch from two sources, score the postings, and let the user triage and track an application. A restart in the middle of scoring must lose no posting.

The behavior is specified in `openspec/changes/rebuild-job-aggregator/`. That change holds six capability specs, the design, and the task list. This plan shows the architecture from `design.md`. A few decisions are still open. See Open Questions at the end.

## Scope

In scope: source adapters, the ingestion pipeline, the candidate profile, two-stage matching, the ranked job interface, and application tracking.

Not in scope: notifications, cover letter generation, file attachments, more than one user, and data import from the first version.

## System overview

One process serves the API, runs the background worker, and serves the built client. One SQLite file holds all state. The server has one module for each capability and a shared kernel. A module calls another module only through its exported interface. Modules hand work to each other through the task queue and report changes through the event bus.

## Two-stage matching

The first version asked the model one question for each posting and stored one number. Every change to the CV or the preferences forced a new model call for every posting. The new design separates what the posting says from how well it fits.

<Columns id="matching-columns">
<Column id="matching-before" label="First version">

One prompt receives the CV text, the preferences, and the posting text. It returns one score from 0 to 100 and two sentences.

The location rules are literal prompt text for one country.

One hash of CV and preferences marks scores as stale. Any change means one model call for each posting.

</Column>

<Column id="matching-after" label="New design">

**Extract** reads only the posting and stores `PostingFacts`. The result does not depend on the profile.

**Constraints** and **score** are code. They read the facts, the preferences, and the weights. They handle location, language, and work arrangement, both hard and soft.

**Judge** reads the facts, the structured profile, and the other soft preferences. It returns three fit scores, matched skills, missing skills, and an assessment.

Two version hashes decide which steps run again.

</Column>
</Columns>

<Callout id="unknown-fact-rule" tone="info">

An unknown fact never excludes a posting. If the posting does not state a location or a language, the hard constraint for that fact does not apply. The detail view shows the extracted facts and the exclusion reason, so the user can check each exclusion.

</Callout>

## Interface and live updates

The client has four routes: `/jobs`, `/board`, `/settings`, and `/activity`. The jobs screen has two panes on a wide screen: the ranked list on the left and the detail on the right. On a narrow screen the detail is its own route. Filters, sort order, and the selected posting are typed search parameters in the address, so a reload restores the view.

The server publishes events such as `run.progress`, `posting.added`, `match.updated`, and `llm.status`. One SSE endpoint forwards them. The client patches the matching query in place. A new score updates its row without a reload. The list changes its order only when the user asks for a refresh, so rows do not move while the user reads.

Triage actions update the interface first and roll back on an error. Each action returns an undo token.

<Callout id="auth-decision" tone="decision">

**Access control is one optional password.** Session token hashes live in the database, so a login survives a restart. Without a password the server binds to `127.0.0.1` only.

</Callout>
